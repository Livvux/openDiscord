# Voice control HTTP draft

This unmerged stack adds `POST /api/voice/control`; it does not activate the Voice provider, a call-session coordinator, E2EE media or a product UI. It must remain draft until the coherent activation gate is accepted. The explicit SFU room ownership and post-commit revocation work in PR62 must be integrated and retested before token-path acceptance is complete.

The strict action union supports `join`, `heartbeat`, `leave`, `token` and `crypto`. Cookie authentication supplies the account and session. Join additionally requires the registered anchor in `x-dm-device` / `x-dm-device-secret`; later actions require `x-voice-member` / `x-voice-secret`. Neither caller identity nor session authority is accepted from the body. Requests require the configured exact application origin and JSON media type. There are no URL credentials, reflected CORS headers or payload/error-object logs.

The outer request budget is 65,536 + 4,096 bytes: the native bootstrap maximum plus bounded action/binding overhead. The real service independently retains its 65,536-byte bootstrap and 8,192-byte other-request limits. Missing or misleading Content-Length does not bypass the actual stream limit. All success/error/method responses must be private and no-store, including framework-generated method denials; the built-server browser regression covers supported method denials and a framework-generated PROPFIND400 denial separately from direct handler tests. The pinned Next.js request constructor rejects TRACE before our Proxy/handler with HTTP 500; an actual isolated CI trace confirmed its response already carries private/no-store directives. This is a platform limitation, not an application 405 or successful Voice operation. Next16.4's `resolveHandler` explicitly rejects unknown methods with400 before userland; the initial actual PROPFIND response had no Cache-Control. An exact-path Proxy response header now supplies private,no-store for this generated rejection, without changing CSP, the matcher or other routes.

`createVoiceHttpClient` holds no enrollment store and opens no DM machine. Callers explicitly supply the current anchor or member possession and an AbortSignal. It sends same-origin cookies, refuses redirects, uses no-store, and cancels response streams on abort/deadline or byte overflow. The default deadline is 10 seconds. Sync is bounded to 64 events of at most 8,448 UTF-8 bytes each, with 4,096 bytes of outer metadata allowance; errors have a 4,096-byte budget. Native response topologies/counts, snapshot namespace/bindings and token room/member/generation are validated before returning data to an owner. Original native/transport IDs and body values are preserved. Unknown-commit retries are the caller's explicit decision; the client performs no retries.

Errors expose stable typed codes. Abort, timeout, protocol, network, current authority denial and conflict are failures. A conflict is not automatically a generation transition. The later call-session coordinator must fence media and obtain an authorized authoritative snapshot before deciding whether an old response can be interrupted; this transport does not own another native queue or relabel arbitrary errors.

Evidence is separated: direct handler tests use actual signed disposable cookies, registered anchors and PostgreSQL service transactions; the public memory-only SDK bootstrap/query/sync traverses the bounded client and real route; TokenVerifier checks actual signed room/member/sources/data=false/expiry claims. Chromium tests create their own accounts through the real signup UI and use only those contexts' cookie jars on desktop/mobile. None of this proves SAS admission, media-key readiness, actual SFU room creation, decoder readiness or a deployed product flow. Those remain later integrated acceptance gates.

The finite public JSON signature contract accepts at most four initial signature keys under only the uploading voice user, including device, all three signing objects, ordinary prekeys and fallback prekeys. Initial IDs need not be stored yet, preserving bootstrap ordering. Later signature uploads still accept only the known own device plus three immutable cross-signing IDs. Query may merge four disjoint initial and four later known entries, so the client accepts at most two signer users with eight keys each. Claim prekeys are returned unchanged and accept only one signer user with four keys. These are serialization/resource bounds, never cryptographic verification or SAS trust. Plain JSON/real DB regressions exercise this edge without passing constructed signatures to any native verifier.
