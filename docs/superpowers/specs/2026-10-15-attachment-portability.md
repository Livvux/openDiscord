# Attachment-complete community portability

Owner-only community export/import already migrates message/settings JSON but deliberately drops binary attachments. Extend it with an explicit complete archive download while retaining legacy JSON compatibility.

Use standard gzip plus bounded newline-delimited JSON records, implemented with Node streams/zlib and existing Zod validation; no archive dependency or filesystem extraction. Version2 records: community structure, message, attachment-start, fixed-size base64 chunks, attachment-end SHA-256, final counts. Identifiers are archive-local references, never storage paths/URLs. Export includes every attachment of each included message; any missing object makes the stream fail without a valid final record. The UI must explain the existing100000-message cap and concurrent-edit boundary rather than claim a transactionally consistent backup. Operational DB+object backups remain distinct.

Export uses keyset message batches and a captured maximum message ID, not a100000-value SQL IN or a400MB content array. Mentions become display names as before. Read private objects only after active owner checks; recheck ownership between batches. Bounded backpressure, cancellation cleanup, server deadline and no-store/download headers apply. No presigned external URLs or public objects.

Import streams compressed input through native gunzip; independently cap compressed and decompressed bytes, record length, message count, attachment count, per-file bytes and total duration. Reject duplicate references, missing/extra files, malformed base64, out-of-order chunks, bad hashes, unknown record types, missing footer and gzip corruption. Never trust declared lengths, image dimensions, content types or filenames. Scan and re-encode imported images with existing media handling; non-images remain forced downloads. Preserve daily per-user quota with existing advisory upload locks.

Stage object rows with uploaderId and null channelId/messageId, which existing authenticated delivery cannot read. Each file stays bounded in memory (current maximum25MB) while scanning/re-encoding; no archive paths reach the filesystem. Do not create a visible community until the entire archive, gzip checksum and reference graph validate. Extend the existing import transaction to create the community/messages and link all staged rows atomically with new local IDs. Legacy JSON retains its explicit missing-attachment note. On failure, remove only known staged objects/rows where removal is confirmed; ambiguous failed writes keep unreachable rows for the existing sweeper. No deletion of unrelated pending uploads.

Tests: actual private filesystem roundtrip with image and arbitrary binary bytes; non-owner export and foreign staged-ID import denied; corrupt/truncated/bomb/duplicate/unresolved archives leave no community; scanner failure and quota failure; private delivery still checks membership; browser download/import roundtrip on desktop/mobile and no app console/network errors. Remote full CI, specialist security review, exact-head release and production readback remain required.

Open design check: choose concrete bounded archive limits that fit the existing500MB daily upload quota, and use a shared per-user admission rate plus bounded per-process import concurrency. Failed imports must not silently bypass quota reservations; retries must explain their wait. Do not weaken existing mutation limits or hold a database transaction open during an entire network upload.

## Design review resolutions

- Limits are symmetric for generated and accepted archives: 256 MiB raw attachments, 400 MiB decoded NDJSON, 384 MiB compressed input, 32 MiB accumulated message/structure metadata, 4 MiB per record, 4096 attachments, 100000 messages. A complete export over these limits fails explicitly; it does not drop attachment payloads. Reply/thread references outside the selected message set use the existing normalization rule and are not treated as missing binary payloads.
- Admit one archive import per process, plus shared per-user rate admission; reuse normal image-processing concurrency and upload quota reservations. No database transaction spans the network upload.
- Bind staged rows to this server-side import's collected IDs. Ignore archive-supplied database IDs. Final transaction acquires the same user lock as normal community creation, rechecks active status and current caps, and links only this import's owned/unlinked rows.
- No eager destructive cleanup after a failed or ambiguously committed final transaction. Unlinked staged rows/objects remain private and retain their quota reservation until the existing one-hour sweeper. Linked objects survive even if the commit acknowledgement was lost. Upload deadline five minutes and final transaction timeout30s keep staging well inside the sweeper TTL.
- Accept one final footer, reject records after it, and commit only after complete native gzip checksum validation. No resumable imports or new background job infrastructure.
